## De quoi il s'agit

RasenGames est une plateforme de jeux d'ambiance sur thème anime/manga, jouée entre amis depuis le web sur des appareils séparés (un onglet par joueur, pas de compte). Déployée sur Cloudflare Workers à l'adresse `rasengames.reesch.com`. Le nom est un jeu de mots sur « Rasengan » — tout nouveau contenu est thématisé anime/manga par défaut, sauf consigne contraire.

## Commandes

```
npm install            # installe les dépendances
npm run dev            # wrangler dev — serveur local avec Durable Objects + assets statiques
npm run deploy         # wrangler deploy — déploiement manuel sur Cloudflare
npm run typecheck      # tsc --noEmit
npm test               # scripts/words-test.mts (règle "même mot") + scripts/smoke-test.js (les 7 frontends contre un DOM bouchon)
node scripts/disconnect-test.mjs   # demande un `npm run dev` en face : hôte réattribué, phase débloquée au départ d'un joueur, sonde /exists
```

`npm test` ne couvre que la règle « même mot » et les frontends contre un DOM bouchon ; c'est ce que lance la CI (`.github/workflows/ci.yml`, typecheck + tests sur push et pull request — elle ne déploie rien). `scripts/disconnect-test.mjs` couvre le serveur mais exige un `npm run dev` vivant (d'où son absence de `npm test` et de la CI) : il pilote de vrais clients WebSocket à travers les chemins de déconnexion qui laissaient un salon figé, plus la sonde d'existence d'un salon. Au-delà, la logique de jeu et le protocole ont été validés pendant le développement avec des scripts Node jetables (`WebSocket` natif, plusieurs joueurs simulés contre `wrangler dev`) et un script Playwright pour le glisser-déposer — ni l'un ni l'autre n'est versionné. Quand tu changes la logique d'un jeu, le plus rapide reste la même approche : lancer `npm run dev` et faire jouer deux ou trois clients WebSocket sur une manche complète.

**Déploiement** : le projet Cloudflare Workers est relié à ce dépôt GitHub (`Loris01100/Rasengames`) via Workers Builds, qui lance `npx wrangler deploy` automatiquement à chaque push sur `main`. Cette liaison a déjà sauté en silence (le tableau de bord Cloudflare affichait une bannière « disconnected from your Git account » tout en continuant à montrer l'ancienne config de build) — si un push ne produit pas de nouveau déploiement, vérifier Settings > Build sur le tableau de bord avant de soupçonner le code. `npm run deploy` marche toujours en secours.

## Architecture

Pile volontairement minimale : Cloudflare Workers + Durable Objects pour l'état temps réel, pas de framework, pas de base de données, pas de bundler. Le backend est en TypeScript ; le frontend est du HTML/CSS/JS écrit à la main par jeu, chargé directement via `<script src>` (aucune étape de build, aucune dépendance npm côté navigateur).

### Routage des requêtes (`src/index.ts`)

Un seul handler `fetch` pour tout le site, piloté par le tableau `GAMES` (`{ slug, namespace }`) :
- `POST /api/<slug>/create` → génère un code de salon unique et le renvoie en JSON.
- `GET /api/<slug>/exists/<code>` → `{ exists }`, transmis au Durable Object du salon. Le client s'en sert avant de rejoindre : un Durable Object naît à la demande, donc sans cette sonde un code mal tapé ouvre un salon fantôme où le joueur attend seul au lieu de recevoir une erreur.
- `GET /ws/<slug>/<code>` → retrouve (ou crée à la volée) le Durable Object du jeu par `idFromName(code)` et lui transmet la requête d'upgrade WebSocket.
- Tout le reste tombe dans `env.ASSETS.fetch(request)`, qui sert `public/`.

Ajouter un mini-jeu veut dire : créer sa classe Durable Object, ajouter une entrée à `GAMES` dans `src/index.ts`, ajouter le binding à l'interface `Env` de `src/env.ts`, et ajouter à la fois une entrée `durable_objects.bindings` et une nouvelle entrée `migrations` (`new_sqlite_classes`) dans `wrangler.toml`.

### Structure d'un jeu (`src/games/<slug>/`)

Chaque jeu est autonome et suit la même forme (voir `undercover/` et `hundred/` comme références) :
- `types.ts` — la forme du `RoomState` persisté dans le stockage du Durable Object, plus `createEmptyRoom(code)`.
- `logic.ts` — des fonctions pures (attribution des rôles/nombres, conditions de victoire, score) sans dépendance au DO ni aux WebSockets, faciles à raisonner isolément.
- `room.ts` — la classe Durable Object. Elle tient en mémoire un tableau `sessions: {ws, playerId}[]` et un `RoomState` en cache (`this.room`), lu et écrit dans `this.state.storage` via `loadRoom()`/`saveRoom()`. Tout message WebSocket qui change l'état se termine par `saveRoom()` + `broadcast()`. `broadcast()` envoie à chaque socket connectée une vue *personnalisée* construite par `buildView(room, playerId)` — c'est là que l'information cachée (ton rôle/mot/nombre par rapport à ceux des autres) est filtrée par destinataire avant sérialisation.
- Les données statiques propres au jeu (`words.ts`, `themes.ts`, etc.).

Chaque `room.ts` réimplémente sa propre plomberie session/join/reconnexion/broadcast plutôt que d'hériter d'une classe de base — les sémantiques de tour, de vote et de déconnexion divergent d'un jeu à l'autre (voir les commentaires dans chaque `room.ts`), et l'abstraction partagée ne valait pas la complexité de généricité. Seul ce qui est *identique* et *porteur* a été factorisé : `src/lib/session.ts` (l'interface `Session` plus `attachSession`, `broadcastState`, `sendError`, `nameTaken`, `promoteWaiting`, `kickPlayer` et `switchGame` — ces sept-là étaient copiés à l'octet près dans les sept `room.ts`, vérifié au diff ; typage générique/structurel, chaque `RoomState` garde sa forme), `src/lib/host.ts` (`reassignHost`, typé structurellement sur les trois champs que tout `RoomState` partage) et `src/lib/throttle.ts` (taille et débit max des messages entrants — rien n'authentifie un client, et chaque message coûte une écriture de l'état du salon ; au-delà du quota les messages sont ignorés sans fermer la socket).

**Un joueur qui part ne doit jamais figer un salon.** Trois règles à respecter dans tout nouveau jeu :
- `handleClose()` appelle `reassignHost(room, player.id)` — l'hôte est le seul à pouvoir démarrer/relancer/exclure/changer de jeu, donc sans successeur le salon est mort.
- toute bascule du type « tout le monde a joué » vit dans une méthode (`maybeAdvancePhase` / `maybeAdvanceStep` / `maybeStartArrange` selon le jeu) appelée **et** à la réception du message **et** dans `handleClose()` : évaluée seulement sur message, elle n'arrive jamais quand c'est le départ du dernier joueur attendu qui la rend vraie.
- `onRestart` accepte n'importe quelle phase sauf `lobby` : c'est la sortie de secours de l'hôte (bouton « Revenir au lobby » du header, rendu par `room-client.js`) pour tout blocage résiduel.

Une alarme (`bomb`, `bac`) passe par `loadRoom()` et jamais par `storage.get("room")` en direct : c'est `loadRoom()` qui recharge la visibilité et rétro-remplit les champs récents. Elle doit aussi savoir s'arrêter quand plus personne n'est connecté, sinon elle se reprogramme dans le vide indéfiniment.

**Piège du code de salon** : le `fetch()` de `room.ts` extrait le code du chemin en prenant le *dernier* segment non vide, et regarde si l'avant-dernier vaut `exists` pour distinguer la sonde d'existence d'un upgrade WebSocket. `src/lib/rooms.ts` (utilisé par `index.ts` pour `/api/<slug>/create`) doit donc sonder `/<slug>/exists/<code>` (le code en dernier) — mettre `/exists` après le code casse silencieusement l'analyse du code (c'est déjà arrivé une fois, voir l'historique git).

**Manches, scores et retardataires** : chaque `RoomState` porte `scores` (points cumulés sur les manches du salon, attribués à la fin de la manche — la règle diffère selon le jeu, voir chaque `room.ts`) et `waiting` (les joueurs arrivés en cours de partie). Les joueurs en attente sont délibérément tenus *hors* de `players`/`playerOrder`, pour que la manche en cours ne puisse pas les voir du tout ; `promoteWaiting()` les fait entrer quand `onRestart` ramène le salon au lobby. Les deux champs sont rétro-remplis dans `loadRoom()` (`??=`) parce que les salons persistés avant leur existence sont relus tels quels.

**Identité du joueur / reconnexion** : rejoindre attribue un `id` et un `token` aléatoires ; le token est renvoyé dans le message `joined` et le client le garde dans `localStorage`, indexé par code de salon. Rejoindre avec un token connu rattache le joueur existant au lieu d'en créer un nouveau — c'est ce qui gère le rafraîchissement et la reconnexion après coupure. Une déconnexion marque le joueur `connected: false` plutôt que de le supprimer.

### Frontend (`public/`)

- `public/index.html` + `public/styles.css` — la page d'accueil et le thème sombre partagé (tokens de design en variables CSS), plus les styles de composants communs (écran de connexion, lobby, lignes de la liste des joueurs, formulaires en ligne) réutilisés par toutes les pages de jeu.
- `public/js/room-client.js` — le global `Room` que chaque page de jeu charge avant son propre `app.js`. Il possède le WebSocket et sa reconnexion, l'écran rejoindre/créer, l'identité en localStorage, le badge de salon, le toast, l'entête « changer de jeu », les lignes de joueurs et le lobby (`Room.init({ slug, minPlayers, maxPlayers, onState })`, puis `Room.send/toast/showScreen/playerRow/renderLobby/showSwitchGame`, plus les `Room.playerId` / `Room.state` vivants). Tout ce qui est identique d'un jeu à l'autre a sa place ici, pas copié-collé dans un huitième `app.js`. Il possède aussi la sonde d'existence du salon sur le bouton « Rejoindre », la reconnexion immédiate sur `visibilitychange`/`online` (le backoff monte à 30 s, il ne doit pas faire attendre celui qui revient — cas mobile classique) et le nettoyage du `localStorage` (dix derniers codes par jeu). Et cinq choses qu'aucun jeu ne connaît : le bouton « Règles » du header (le contenu vient du `<template id="rules">` de la page, déplacé dans un `<dialog>` natif — la top layer le fait passer au-dessus des `.card` sans le contournement de `suggest.js`, et Échap plus le fond assombri sont gratuits ; `npm test` vérifie que chaque page en porte un), le bouton « Revenir au lobby » de l'hôte (envoie `restart`, affiché hors lobby seulement), le bouton « copier le lien » (construit en JS, ajouté à côté de `#lobby-code`, puisque `?room=CODE` était déjà géré au chargement), l'étiquette de score cumulé (`state.scores`) sur chaque ligne de joueur, et l'écran d'attente — un joueur qui arrive en cours de partie est retenu côté serveur dans `room.waiting` et le client lui affiche un `#screen-waiting` généré au lieu d'appeler le `onState` du jeu.
- **Balises de partage** : le lien d'un salon se colle dans une conversation de groupe, donc chaque `index.html` porte ses `og:` (image commune `public/og.png`, 1200×630) et le favicon `public/favicon.svg`. `npm test` échoue si une page de jeu en manque.
- `public/js/anilist.js` — `Anilist.suggest(text, kind)` (complétion de noms) et `Anilist.setImage(img, name, kind)` (illustration), qui interrogent tous deux graphql.anilist.co **depuis le navigateur du joueur**, avec un cache par onglet. Ça tournait dans le Worker jusqu'à ce qu'AniList réponde `403 "You have been manually blocked"` : les Workers partagent quelques IP de sortie et AniList les blackliste, donc aucun throttling ni cache de notre côté n'y change quoi que ce soit. Depuis le navigateur, chaque joueur utilise sa propre IP et le support CORS d'AniList. Les salons ne stockent donc plus d'URL d'image dans leur état — le client résout l'illustration à partir du nom qu'il affiche déjà. Quand un joueur choisit une suggestion, l'entrée exacte voyage avec le mot sous forme d'`anilistRef` (`"character:83801"`, validé côté serveur, stocké en `wordRef`/`proposalRef`) et l'emporte sur la recherche par nom : chercher « King » renvoie Lelouch, dont les alias contiennent « Black King », et pas le King de Nanatsu no Taizai. Les mots tapés à la main n'ont pas de ref et retombent sur le nom. `Anilist.exists(name, kind, strict)` (Alphabombe, 1 à 100) répond `found`/`notfound`/`unknown` — il échoue *ouvert* sur `unknown`, parce qu'une vérification rate-limitée ne doit pas figer une partie, ce qui fait du budget de requêtes AniList une partie de la fonctionnalité : la recherche demande personnages et animes en une seule requête, et les deux jeux sautent la vérification quand le mot vient du menu de suggestions (c'est déjà une entrée AniList). Les mots d'Undercover n'ont aucune ref, leurs images sont donc résolues par nom — et seulement pour les catégories `character` et `anime`, puisqu'AniList n'a pas d'entrée pour un groupe ou un lieu et répondrait « Akatsuki » par un personnage de ce nom (d'où `wordCategory` dans son `RoomState`). `scripts/` n'a pas de test en direct là-dessus (il faudrait le réseau) ; `npm test` bouchonne le point d'entrée.
- **Piège CSS** : chaque `.card` joue `animation: fadeInUp ... both`, et le `transform` retenu de la dernière keyframe fait de chaque carte son propre contexte d'empilement — un popup en `position: absolute` dans une carte ne pourra jamais peindre par-dessus la carte *suivante*, quel que soit son `z-index`. `suggest.js` contourne ça en posant une classe `.suggest-open` sur la carte hôte tant que son menu est ouvert ; faire pareil pour tout futur popup.
- `public/js/suggest.js` — `Suggest.attach(input, kindOf)` accroche un menu de suggestions sous un champ texte et le remplit depuis AniList via `Anilist.suggest` (3 caractères minimum, 350 ms de debounce, cache dans la page). Branché sur les champs de personnage de Qui suis-je, Détective et 1 à 100. Il n'utilise délibérément *pas* de `<datalist>` natif : les navigateurs Firefox ne rafraîchissent pas un popup de datalist déjà ouvert quand ses options sont injectées après la frappe, donc les suggestions n'apparaissaient jamais là-bas. L'écouteur `keydown` est en phase de capture pour que la validation par Entrée passe avant le handler « Entrée = envoyer » du jeu sur le même champ. En plus des personnages, le menu liste jusqu'à trois animes ; en ouvrir un (plutôt que le choisir) remplace le menu par le casting de cette série, ce qui permet à quelqu'un qui connaît l'anime mais pas l'orthographe d'y arriver en deux clics — le titre de l'anime reste sélectionnable en haut de cette liste.
- `public/games/<slug>/{index.html,style.css,app.js}` — un jeu par dossier, liant la feuille de style partagée puis la sienne. `app.js` ne contient que les écrans, messages et sons de ce jeu : une fonction `render(state)` qui reconstruit intégralement le DOM de l'écran concerné à partir du dernier état poussé par le serveur, à chaque message (pas de diffing ni de DOM virtuel — l'état et le nombre de joueurs sont assez petits pour que ça reste simple et correct). Les écrans sont des `<section id="screen-*">` basculés par `Room.showScreen(id)`, qui ajoute ou retire une classe `hidden`.
- La ligne en glisser-déposer de « 1 à 100 » (`public/games/hundred/app.js`) utilise volontairement une seule paire d'écouteurs `pointermove`/`pointerup` sur `document`, plutôt que des écouteurs par carte avec `setPointerCapture` — la capture ne cantonnait pas les événements à une seule carte de façon fiable dès que la carte tirée était réinsérée ailleurs dans le DOM en plein geste, et d'autres cartes réagissaient au même événement. Garder ce schéma si on étend cet écran.

**Chrono et écritures (Petit Bac)** : la vue envoie `endsIn` (durée restante) et non `endsAt` (instant absolu) — l'horloge d'un téléphone peut être décalée de plusieurs minutes et affichait alors un compte à rebours faux ; le client ancre la deadline sur son horloge à la réception. Et `onAnswer` ne sauvegarde pas à chaque frappe : les réponses sont privées jusqu'à la fin de la manche, donc l'écriture est groupée (2 s) via `scheduleAnswerSave()`. Ça suppose que le DO reste vivant entre-temps, ce qui est le cas tant que des WebSockets y sont attachés sans hibernation.

### Note sur le stockage des Durable Objects

`wrangler.toml` utilise `new_sqlite_classes` (Durable Objects adossés à SQLite) pour les sept classes de salon comme pour la registry — c'est le défaut actuel pour un nouveau projet Workers, et c'est aussi ce que `wrangler dev` provisionne en local.
